## 1. 问题与目标

### 1.1 问题

使用者希望减少手动检查仓库状态和整理发布版本的工作。当前痛点的频率、耗时和错误率未提供，不编造收益数据。插件应回答：当前在什么仓库、发生了什么变化、相对哪条基线分析、下一版本为何这样建议、哪些地方仍需人工判断。

### 1.2 成功判据

| 目标 | 可观察结果 | 对应需求 | 验证方式 |
| --- | --- | --- | --- |
| 自动发现并反映仓库状态 | 在允许范围与已确认触发策略下更新状态；无仓库、无提交、无权限均有明确结果 | REQ-001、REQ-002、REQ-003、REQ-005 | 本地隔离夹具与宿主集成验证 |
| 版本建议可解释、可复现 | 给出固定 HEAD、基线、提交证据、规则版本和阻塞原因；不从不完整输入生成确定版本 | REQ-006、REQ-007、REQ-008、REQ-009、REQ-010 | 固定历史夹具与结果断言 |
| 不越权操作用户仓库 | Git 采集本地且不自动联网；导出显式选择；数据进入 Codex / 模型的范围单独确认；不自动发布 | REQ-012、REQ-013、NFR-001、NFR-002 | 区分 Git 子进程与宿主的数据通道后分别审计 |
| 具备 Codex 工作流内可用流程 | 选择仓库、查看状态、审查建议、人工复核、导出和暂停可完成闭环 | REQ-004、REQ-011、REQ-014、REQ-015、REQ-016 | 在已核实支持的 Codex 接入方式下验证，不假设存在 IDE 面板 |

性能收益与版本决策准确率的量化目标暂无数据，不能当作已承诺指标。

## 2. 范围与非目标

### 2.1 建议本次范围

1. 单一发布单元的本地仓库检测；允许工作区有多个仓库，但一次只分析用户当前选择的仓库及工作树。
2. 在 Codex 工作流内触发本地检查并保留手动刷新；自动运行时机待 Q-006，不能将已选择的本地范围当成持续后台监控授权。
3. 当前 Git 状态、可达版本标签、基线到目标提交的变更信号。
4. 下一版本建议与变更说明草稿、证据和风险清单；人工调整与带快照标识的本地报告导出。不规划未来需求与发布日期。
5. Git 本地只读访问、异常恢复、确定性与 Codex 接入兼容性验证；宿主 / 模型数据边界单独受 Q-005 约束。

### 2.2 明确不做

- 不自动执行 fetch、pull、push、commit、reset、clean、stash、checkout、tag、rebase、发布或远端写操作。
- 不扫描整台机器、主目录或未由用户选择的仓库；不安装常驻守护进程或定时任务。
- 不把未提交文件内容当作已发布变更；不默认读取源码全文或将数据送到模型服务。
- 不声称已确认真实远端同步状态、CI 通过、包已发布或实际 API 向后兼容。
- 不提供多包独立版本、自动合并发布、跨仓库版本依赖求解或自动回退。
- 不在未收到未来需求和资源约束时生成真实产品路线图、承诺日期或发行里程碑。

### 2.3 后续候选，不构成本次承诺

多包 monorepo、预发布渠道自动递增、版本文件写入、changelog 写回、授权 fetch、CI / 代码托管集成、API 差异分析、可选 AI 辅助摘要、未来需求路线图。任何联网、写仓库或模型接入需另行评估与确认，不能由开关默认开启。

## 3. 角色、场景与规则

### 3.1 角色与权限

| 角色 | 可以做 | 不可以做 | 依据 |
| --- | --- | --- | --- |
| 使用者 / 维护者 | 选择有权访问的工作区，启用检测，审查建议，输入人工理由，导出报告 | 借插件绕过文件权限、仓库信任或宿主授权 | 宿主权限与操作系统已有权限；具体信任机制待 Q-001 |
| 插件 | 在批准范围内读取所需元数据，计算建议，维护受限会话状态 | 自动修改仓库、外发元数据、提升权限或声称获得人工批准 | REQ-013 与非功能约束 |
| 发布负责人 | 在插件之外确认版本、执行实际发布 | 将“建议”直接视为发布授权 | 当前方案不包含发布执行器 |

不建立独立账号系统；如宿主需要身份或云端能力，须重开范围与权限评审。

### 3.2 主场景

1. 使用者打开受支持宿主中的工作区，明确选择或启用允许分析的范围。
2. 插件发现候选仓库，使用者选择目标；展示工作树、分支 / HEAD、变更与数据新鲜度。
3. 插件在已确认触发策略下自动重新检测；手动刷新可独立使用，暂停后不再发起新的自动检测。
4. 使用者请求版本规划；插件冻结本次输入快照，显示本地候选基线及筛选原因。
5. 基线和策略充分时分析提交，给出候选 bump、候选版本、变更分组、风险与待复核项。
6. 证据不足时显示待确认原因，保留能确定的事实，但不输出“确定可发布”结论。
7. 使用者可进行显式人工调整并导出报告；仓库变化会使旧建议标为陈旧，人工确认不得跨快照自动沿用。

### 3.3 状态与不变量

| 对象 | 合法状态 / 转换 | 不变量 |
| --- | --- | --- |
| 检测会话 | 未启用 → 检测中 → 可用；可用 ↔ 刷新中；任意运行态可暂停、停止或报错 | 暂停后不新增自动任务，停止 / 关闭工作区后释放监控；旧请求不能覆盖新请求 |
| 快照质量 | 完整 / 不完整 / 陈旧；每个快照带工作树身份与采集代次 | 多命令采集不宣称文件系统原子快照；变化无法稳定采集则标陈旧或不完整 |
| 版本计划 | collecting → needs_review / suggested / no_release；任一结果可变 stale | suggested 只表示规则计算完成，绝不表示已批准或已发布 |
| 人工复核 | 未复核 → 对当前指纹已复核；指纹变化则失效 | 版本、范围、分类或策略发生变化均不能无提示继承旧确认 |
| 本地报告 | 预览 → 选择目标 → 写入成功或失败 | 不覆盖未授权目标，不写入工作树或 Git 元数据目录，不把导出失败显示为成功 |

## 5. 输入、输出与版本规则

### 5.1 输入与边界

| 输入 | 约束与默认处理 | 未知或非法处理 |
| --- | --- | --- |
| 工作区与选择目标 | 只来自宿主明确提供或用户选择的路径；遍历边界、深度与符号链接策略待 Q-002、Q-004；不扫全盘 | 超边界拒绝；未知时只登记建议配置，不自动开启扫描 |
| Git 程序与环境 | 使用宿主可信位置或经确认的程序；最小版本与能力探测待 Q-004；仓库元数据不是可执行指令 | Git 不可用或能力不足报告不支持；不下载 Git、不改 PATH、不修改信任配置 |
| 仓库身份 | 用工作树根路径、实际 Git 目录和 common-dir 区分；子模块和 linked worktree 不合并为同一个工作树 [S2] | bare 仓库本次仅显示“无工作树，当前模式不支持”，不尝试转换 |
| 本地 refs、HEAD 与标签 | 读取本地对象和引用；对象 ID 视为 Git 返回的不透明标识，不假定固定哈希长度 | 浅历史、缺对象或遍历超预算标记不完整，不能默认远端无新增 |
| 基线选择 | 显式确认的完整标签引用优先；候选建议规则见下文 | 无合法基线、非祖先、解析失败或重复归一版本冲突进入 needs_review |
| 发布策略 | 规则标识、版本方案、允许标签前缀、0.x 与预发布策略均须确认 | 未确认策略只输出事实和待决项，不自行决定正式版本 |
| 人工输入 | 版本、分类、原因，作为数据而非 shell 参数或脚本；非空理由不能为空白 | 非法 SemVer、低于 / 等于当前基线或与现有标签冲突时拒绝成为有效目标 |

### 5.2 Git 状态与触发策略

- 建议使用适合机器解析的状态接口；Porcelain v2 可输出分支与工作树信息，NUL 分隔用于特殊路径处理 [S1]。界面不把原始 Git 输出直接当 HTML。
- upstream 信息缺失、跟踪引用缺失和领先 / 落后未知是不同状态；本地跟踪引用不代表刚查询过服务器。
- 使用环境已确认为 Codex 工作流。待 Q-006 选择按工作节点检查、持续监控或先手动检查；只有实际接入能力已验证的触发方式才可承诺。不能将普通 Skill 读取或用户选了 Codex 等同于存在可靠文件事件 / 生命周期钩子。
- 触发点、debounce、重扫和轮询参数仍待 Q-004、Q-006；没有运行能力时显示限制或降级，不悄悄创建后台服务、定时任务或全局 Git hook。
- 工作区事件与共享 Git 元数据变化都可能影响结果；仅监听一个 `.git` 文件不是足够实现策略。无法可靠自动捕获时显示降级，并保留手动刷新。
- 建议每个工作树最多一个进行中的采集和一个合并后的最新待处理请求；没有变化的结果不重复弹通知。此为建议并发策略，不是已测性能承诺。
- 暂停停止新的自动调度；用户主动刷新是独立动作。停止或关闭工作区取消当前任务、清理队列和订阅，迟到回调不得复活会话。

### 5.3 发布基线候选

以下为单发布单元、稳定版本标签模式的候选算法，需 Q-003 确认后启用：

1. 仅使用本地、可解析到提交、属于选定发布命名空间并可达目标 HEAD 的标签；同时处理轻量和附注标签，不把标签日期当成版本高低。
2. 命名空间可配置是否接受前缀 `v`；裸 SemVer 名称和 `v` 前缀同时存在时，归一结果必须唯一。不同对象映射同一版本或 build metadata 引起优先级并列时，转人工确认，不能随意挑一个。
3. 对合法稳定版本按 SemVer 优先级选最大值作为候选，向用户展示选中 / 排除原因；明确这只是本地标签候选，不证明包已发布或标签签名可信。
4. 手动基线必须解析为完整本地引用及提交，并满足范围和可达性约束；输入不能直接拼接命令字符串。
5. 不可达的更高标签不作为当前基线，但若下一版本在任何本地相关标签中已被占用，显示版本冲突，不自动跳号。
6. 无标签、只有预发布标签、主版本为零、monorepo 多发布域或版本文件与标签不一致时，保留候选证据并等待策略，不假定初始版本为 0.1.0 或 1.0.0。

### 5.4 提交集合与分类

- 固定基线对象 B 和目标对象 H，分析集合为“从 H 可达、但从 B 不可达”的提交，即 Git 的双点范围语义 [S3]。不按提交时间筛选，不默认只看 first-parent。
- 按对象身份去重；merge 及其父链的提交不能重复计数。普通 merge 消息不是可自动忽略的业务变更证据；对未分类消息显示复核，不静默扩大排除规则。
- 不读取工作区源码全文推断未来发布；dirty 仅产生“未提交内容未纳入”风险，不改变已提交集合的计算。
- 若采用 Conventional Commits：`fix` 提供 patch 信号，`feat` 提供 minor 信号，`!` 或合法 `BREAKING CHANGE` / `BREAKING-CHANGE` footer 提供 breaking 信号；breaking 优先，不限提交 type [S5]。
- 其他合法 type 不自动升级为 patch；非规范消息、revert、混合 / 自相矛盾证据保留并进入人工复核。不得仅通过标题包含 `break` 等单词判断 breaking。
- 分类属于“提交描述声称的意图”，不是 API 差异证明。用户可逐条复核，系统保留修改前后的理由与对应对象。

### 5.5 下一版本建议

候选稳定策略只针对已确认的 `major >= 1` 正式版本：major 高于 minor，高于 patch；升级高位时低位归零。无提交为 no_release；仅含无隐式 bump 的 type 时为 needs_review / 无自动递增依据，不自动加 patch。SemVer 对公共 API、稳定版本和 0.x 的定义见 [S4]；不能把 0.x 套用稳定版 breaking 规则。

| 输入条件 | 机器输出 | 额外状态 |
| --- | --- | --- |
| 完整范围，仅明确 fix，基线 1.4.2 | 1.4.3，patch | suggested；仍不是发布批准 |
| 完整范围，含 feat 与 fix，基线 1.4.2 | 1.5.0，minor | suggested |
| 完整范围，含明确 breaking 信号，基线 1.4.2 | 2.0.0，major | suggested；要求人工确认真实兼容影响 |
| B 等于 H，无新增提交 | candidateVersion 为 null，bump 为 none | no_release，不伪造发布 |
| 有非规范、revert 或不完整范围 | 可保留已识别信号的 provisionalCandidate，但正式 candidateVersion 为 null | needs_review，列出缺口 |
| 只有 docs / chore 等无默认 bump type | candidateVersion 为 null | needs_review，等待项目策略或人工版本决定 |
| 无基线、0.x、预发布、重复标签或目标版本占用 | candidateVersion 为 null | needs_review，列出明确原因 |

表中版本是隔离测试样例，不是用户仓库数据或插件发行承诺。人工给出的更低 bump 不能抹去规则冲突；可导出“待复核提案”，不能改标为无争议 suggested。

### 5.6 计划输出契约

推荐内部对象与 JSON 导出共享下列逻辑字段；具体语言类型及宿主消息协议待实施设计，不预设网络 API：

| 对象 | 必需字段 / 语义 |
| --- | --- |
| RepoSnapshot | schemaVersion、repoKey、worktreeKey、generation、capturedAt、headOid 或 null、branchState、statusSummary、upstreamState、historyCompleteness、warnings |
| AnalysisFingerprint | worktreeKey、固定 HEAD / 基线对象、归一标签集合、提交集合摘要、工作树状态摘要、本地 upstream 引用、有效策略版本、人工调整版本；输入变化即失效 |
| VersionPlan | planId、fingerprint、baseRef、baseVersion 或 null、targetOid、commitCount、classificationEvidence、bump、candidateVersion 或 null、provisionalCandidate 或 null、decisionState、releaseNotesDraft、reviewItems、riskChecks、policyVersion |
| ReleaseNotesDraft | 相对本次 B/H 的变更条目，按已识别分类分组；每条有提交引用，breaking 和未归类信息不隐藏；未提交内容不声称已交付，人工改写保留来源；术语和自然语言风格不影响核心分类 |
| ManualReview | fingerprint、原始建议、用户选择、理由、复核记录；复核主体由宿主真实上下文或用户自报并注明来源，不伪造身份认证 |
| ExportEnvelope | schemaVersion、snapshot / plan、导出时间、未决项与事实 / 建议区分、来源声明；不含凭证、远端带认证 URL 或无必要绝对路径 |

语义相同的输入可以有不同采集时间或本地 planId，但建议、分类、提交集合和稳定排序必须一致。日期明确时区；输出显示脱敏仓库别名，不以完整机器路径作为公开报告标识。

### 5.7 导出与数据生命周期

只允许用户显式指定的、位于受管工作树与真实 Git 元数据目录之外的文件目标；linked worktree 的共享目录也在禁止写入范围。目标为符号链接或无法确认边界时拒绝，不悄悄跟随；覆盖已存在文件需要单独确认。

建议采用同目录临时文件再原子替换，成功后才返回完成；无安全写入保障时拒绝而非退回不安全写法。导出只写报告，不写版本文件。默认原始元数据仅留在会话内存；如需持久化设置 / 缓存，存储位置、保留期与清除方式待 Q-004，未确认不擅自设定期限。

## 8. 验收标准

以下均是待执行目标，不是通过记录。拟采用的配置与主机平台尚未确认，所涉场景必须在基线就绪后执行。所有测试数据均为隔离合成夹具。

### AC-001：明确范围的仓库发现

- 关联需求：REQ-001。
- Given：启用范围内有普通目录、一个仓库及其子目录、嵌套仓库、已初始化子模块和两个 linked worktree；范围外另有仓库。
- When：按已确认发现策略检测并分别选择结果。
- Then：只列出边界内目标；同一工作树子目录去重，子模块 / 嵌套仓库分别标识，共享对象库的 worktree 不误合并；普通目录无异常。
- 验证：对比独立 Git 身份探测与候选清单；保留发现边界及去重证据。扫描策略未定时本项阻塞。

### AC-002：工作树状态不冒充远端事实

- 关联需求：REQ-002。
- Given：依次配置正常分支、detached、无 upstream、丢失跟踪引用，以及合成暂存 / 未暂存 / 未跟踪 / 冲突状态。
- When：采集状态；另在测试远端新增提交但本地不 fetch。
- Then：分类与真实本地 Git 状态一致；未知计数为未知，不为零；ahead/behind 注明依据本地引用，不声称检测到尚未获取的远端提交。
- 验证：状态对象与 UI 标签断言；保留网络无访问记录。

### AC-003：启停、事件合并与降级

- 关联需求：REQ-003。
- Given：已确认宿主触发策略、debounce 和监听失败处理，有可控事件源。
- When：连续触发变化、暂停、手动刷新、恢复、监听报错、停止并关闭工作区。
- Then：重复事件合并；暂停不自动调度但手动刷新可用；监听失败显示降级；停止后无新任务、订阅或迟到回调复活。
- 验证：虚拟时钟与宿主集成测试的调度 / 订阅记录；未知触发参数前不得填通过。

### AC-004：并发、身份与陈旧结果

- 关联需求：REQ-004。
- Given：同一对象库的工作树 A / B，各有独立分支；A 的旧采集比新采集晚返回。
- When：切分支、更改标签或基线、取消任务并切换工作树。
- Then：A / B 状态不串用；只发布当前代次完整结果；旧人工复核失效；不稳定快照标为陈旧或不完整。
- 验证：受控乱序执行与指纹断言，记录旧结果被拒绝的证据。

### AC-005：缺少 Git 或历史时不伪造结果

- 关联需求：REQ-005。
- Given：Git 缺失 / 能力不足、不可访问仓库、信任拒绝、bare、无提交、浅历史、缺失对象分别独立作为输入。
- When：请求检测和规划。
- Then：返回对应明确原因；无 HEAD 不生成提交范围；历史不全不宣称完整；不改信任配置、不安装 Git、不发起补对象网络请求。
- 验证：隔离夹具及失败注入，记录错误码、文件和网络审计。

### AC-006：基线按版本与可达性选择

- 关联需求：REQ-006。
- Given：单发布域上有可达 1.9.0 与 1.10.0、不可达 9.0.0、附注 / 轻量标签、重复归一版本和非法标签；这些情况分开测试。
- When：请求候选基线并尝试合法 / 非祖先手动选择。
- Then：正常案例候选为 1.10.0 而非字符串或日期最大值；不可达不作基线；同版本歧义和非法手动基线给出明确原因，不随机选用。
- 验证：标签 → 版本 → 对象 → 可达性及排除原因断言。

### AC-007：提交集合精确且固定

- 关联需求：REQ-007。
- Given：固定 B / H 的分支合并 DAG，含共享祖先、merge 与 dirty 文件；另有不可完整遍历的历史样本。
- When：分析 B 到 H，并在采集后修改实时 HEAD。
- Then：结果等于固定对象的可达差集，按对象去重，不按日期排除；dirty 不计入；实时变化使旧计划陈旧；截断不能当完整。
- 验证：与独立 Git 对象集合比较，保留对象清单和完整性字段。

### AC-008：提交信号与未知项可追溯

- 关联需求：REQ-008。
- Given：fix、feat、带 scope / !、合法两种 breaking footer、docs、普通消息、revert、普通 merge 和含类似 breaking 单词但不符合语法的消息。
- When：应用已确认的提交分类策略。
- Then：依据规范识别信号；breaking 不受 type 限制；普通词语不误判；其他 type 不默认 patch；未知与 revert 留在复核清单，不丢失原对象证据。
- 验证：固定消息集的分类和原因断言；不调用模型或网络解释成事实。

### AC-009：稳定版本、空集与未定策略

- 关联需求：REQ-009。
- Given：基线 1.4.2，分别提供仅 fix、含 feat、含 breaking、空提交集、仅 docs、非规范、0.x、预发布、无基线和目标版本已存在等独立样本。
- When：请求下一版本建议。
- Then：前三项依次为 1.4.3 / 1.5.0 / 2.0.0；空集 no_release；其余按第 5 节返回 needs_review 和 null 正式候选，不擅自跳号或初始发行。
- 验证：完整样本表和候选 / 状态断言；策略未确认前不可视为产品测试通过。

### AC-010：计划结构与可解释性

- 关联需求：REQ-010。
- Given：固定完整输入及策略，另有带未决项的输入。
- When：重复生成计划并打开证据详情。
- Then：必要字段和变更说明草稿完整；版本建议与每条变更说明能回溯提交、规则与基线；未知 / breaking 单列，未提交功能不声称已交付；核心结果一致，不生成未来需求或日期。
- 验证：契约与语义快照对比，忽略明确列出的采集时间 / 非语义 ID 字段。

### AC-011：人工调整不抹掉冲突

- 关联需求：REQ-011。
- Given：机器候选 major，用户尝试无理由、低版本、非法格式、已占用版本及合法调整。
- When：提交人工选择，然后改变 HEAD 或策略。
- Then：无理由或非法目标被拒绝；低于规则建议保留冲突并 needs_review；合法选择保留前后证据；输入变化后旧复核失效。
- 验证：输入校验、冲突状态与指纹绑定测试，不伪造用户身份。

### AC-012：显式、安全的报告导出

- 关联需求：REQ-012。
- Given：完整或待复核计划、外部目标、已存在文件、工作树内目标、共享 Git 目录、符号链接目标及磁盘写失败。
- When：预览、取消、选择路径、确认覆盖或触发失败。
- Then：仅明确允许且经必要确认的外部目标可写；取消无写入；越界 / 链接拒绝；失败不冒充成功；Markdown / JSON 都保留未决状态和快照身份。
- 验证：隔离目录内容 / 哈希、导出结构与失败恢复检查；无生产数据。

### AC-013：整个流程只读且离线

- 关联需求：REQ-013。
- Given：合成仓库、所有工作树和真实 Git 目录已建立前置快照，partial clone 缺对象与外部助手配置分别受控注入。
- When：发现、自动刷新、规划、取消和错误恢复；不执行报告导出。
- Then：工作树、索引、refs、标签和配置内容未被插件改变；无网络、fetch、写命令、发布或任意助手执行。不能仅凭“使用了只读命令名”判通过。
- 验证：前后内容与引用对比、子进程和网络审计；不比较读取可能影响的访问时间。

### AC-014：可完成的宿主交互

- 关联需求：REQ-014。
- Given：使用方向已确认为 Codex 工作流，Q-004、Q-006 对应接入能力 / 运行方式已核实，提供该接入方式的真实测试环境。
- When：用户从启用开始，完成选择仓库、查看状态、规划、打开证据、调整、导出、暂停和恢复。
- Then：每一步在 Codex 交互或获确认的配套入口可完成，显示状态和错误恢复；版本建议和变更说明都可查看，不把建议显示成已发布；不要求未证实存在的原生面板。
- 验证：Codex 工作流端到端及适用键盘路径记录；当前接入与运行方式未定，本项未执行且相关实施阻塞。

### AC-015：配置有效性与失效范围

- 关联需求：REQ-015。
- Given：已确认默认策略、配置存储和资源预算，另有负数预算、越界路径、非法前缀策略等无效输入。
- When：更新配置及重启会话。
- Then：先校验再生效，无效项保留最后有效值并提示；合法规则变化使旧计划陈旧；持久化仅按批准位置和字段进行。
- 验证：配置校验、迁移 / 重启及指纹测试；默认值未定时不声称完成。

### AC-016：风险检查与发布状态分离

- 关联需求：REQ-016。
- Given：dirty、冲突、历史不足、未确认基线、目标冲突和未接入 CI 的独立场景。
- When：查看计划与导出。
- Then：已观察风险、阻塞项与未知测试 / 发布状态清晰分离；脏文件不当作提交；不展示“CI 通过”“可安全发布”或“已发布”等无证据结论。
- 验证：计划风险字段与展示 / 导出的一致性断言。

### AC-017：元数据最小化与隐私

- 关联需求：NFR-001。
- Given：Q-005 的宿主 / 模型数据许可与脱敏规则已确认，合成提交与路径含敏感样例，远端 URL 含模拟凭证。
- When：正常运行、报错和导出脱敏报告。
- Then：Git 层不联网；进入 Codex / 模型的内容不超过明确批准范围，无凭证或原始敏感日志，不读取非必要源码；缓存和预览按批准规则。若数据边界与所选 Codex 运行方式冲突则明确阻塞，不用“本地检测”掩盖传输。
- 验证：文件 / 网络 / 日志与宿主 / 模型内容通道分别审计；无法审计的环节标未知或阻塞，测试不得使用真实 token。

### AC-018：不可信元数据与进程边界

- 关联需求：NFR-002。
- Given：路径含空格、换行及 shell 特殊字符，消息含 HTML / 指令文本，仓库配置含可触发外部辅助程序的项。
- When：采集、分类与显示；同时模拟不能安全禁用外部行为的 Git 能力组合。
- Then：输入只当数据处理；无额外命令、脚本、pager 或助手执行，无 UI 注入；不能满足安全隔离则明确不支持，不自动放宽。
- 验证：隔离进程监视与 UI / 参数断言；当前没有实现，不能写安全通过。

### AC-019：有界资源与确定性恢复

- 关联需求：NFR-003。
- Given：可控事件风暴、错误、重复请求、乱序返回及固定分析输入。
- When：运行、取消、停止和重试。
- Then：单工作树并发和队列不超过确认上限；停止后无活动订阅 / 任务；无半成品替换有效结果；固定输入核心结果不变；时限按 Q-004。
- 验证：队列 / 子进程计数、虚拟时钟、失败注入与重复结果检查。

### AC-020：能力矩阵与可访问性

- 关联需求：NFR-004。
- Given：已批准的宿主、操作系统、Git 能力矩阵及不支持样本。
- When：逐组合安装 / 加载、完整流程和键盘操作，并探测不支持能力。
- Then：承诺组合均有真实结果；不支持项有明确提示；键盘 / 焦点 / 状态文本符合选定宿主约定。
- 验证：矩阵测试记录和专项检查；矩阵未批准前本项阻塞。

### AC-021：性能预算与超限语义

- 关联需求：NFR-005。
- Given：Q-004 指定的设备、仓库规模、标签 / 提交数量、缓存状态、负载、采样与统计方法。
- When：执行发现、状态、规划、重复事件、取消与超预算案例。
- Then：达成已确认预算，或在约定边界返回明确超预算 / 不完整；不偷偷截断为完整版本计划。
- 验证：原始测量与统计报告；所有数值待真实决定，当前不能给出通过阈值。
